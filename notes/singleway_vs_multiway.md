# Single-way and multiway evolution in G1-G4 and in this repository

This note defines single-way and multiway evolution, lists which mode each part of G1-G4 uses, states which findings of `FINDINGS.md` depend on the update order, and describes the evolution operators of the Lean library.

Paper files: G1 = `papers/gorard_2004.14810.txt`, G2 = `papers/gorard_2011.12174.txt`, G3 = `papers/gorard_2102.09363.txt`, G4 = `papers/gorard_2303.07282.txt`. Status labels follow `STATUS_OF_GORARD_CLAIMS.md`.

## 1. Definitions

Fix a set of rules R and an initial hypergraph s_0.

- Single-way evolution: a sequence s_0 → s_1 → s_2 → ..., where each step applies a set of matches chosen by an update order (in SetReplace, the `EventOrderingFunction`). The causal graph of the evolution has the events as vertices and an edge from event i to event j when j consumes a hyperedge created by i.
- Multiway evolution graph: the directed graph whose vertices are states, with an edge from s to every state obtained from s by one application of a rule at one match. Every path from s_0 is a single-way evolution.
- Branchial graph: for a given step of the multiway evolution graph, the graph on its states in which two states are joined when they share an ancestor.
- Each path through the multiway evolution graph has its own causal graph.

G1 Definition 9 (lines 458-461) defines a multiway system as causal invariant when "the causal graphs that it generates (i.e. the causal graphs generated by following every possible path in the multiway graph, corresponding to every possible updating order) are all, eventually, isomorphic". G2 Definition 22 (lines 1143-1145) states the same definition.

## 3. Use of causal invariance

When a rule is causal invariant, every path through the multiway evolution graph eventually gives an isomorphic causal graph, and a statement about one causal graph holds for all of them. G1 §3.3 assumes causal invariance (line 2170) as a hypothesis of its argument. For a rule without a proof of causal invariance, a statement about one single-way causal graph concerns that update order only.

For the rule of G3 line 6202, the following hold in every evolution and every update order (PROVED, `Refutations/F7NamedRuleStructure.lean` and `CausalHistory.lean`). The edge count stays at its initial value N (`Refutations.gorardNamedRule_applications_preserve_size`). Every antichain of the causal graph has at most N/4 events (`CausalHistory.gorardNamedRule_antichain_card_le`). At most 5^t events lie within directed distance t of an event (`CausalHistory.gorardNamedRule_ball_card_le`). The antichain bound limits the events at each longest-path distance from an event, and the cone counts shortest-path distance, so the antichain bound does not imply linear cone growth. Linear cone growth is OPEN, stated as `CausalHistory.GorardNamedRuleConeGrowthLinear`.

Each path through the multiway evolution graph is a single-way evolution, so the PROVED bounds hold on every branch.

## 5. Evolution operators of the Lean library

- `MultiwayExec.multiwayStep` (`MultiwayExec.lean:142`) returns every state obtained by one application of one rule at one match. `multiwayEvolve` iterates it without merging equal states.
- `MultiwayExec.singleWayStep` (`MultiwayExec.lean:227`) applies a maximal set of edge-disjoint matches, chosen greedily in the order of the rules and of `allMatches`. Edges created in the step are not matched in the same step. This is the update scheme G2 line 1021 describes as its default. On the 4-cycle seed it fires one of the four matches of the rule of G3 line 6202 and the edge count stays 4.
- `MultiwayExec.fireAllStep` (`MultiwayExec.lean:247`) applies every match found in the input state, including matches that share edges, with `fireAllEvolve`, `tracedFireAllStep`, `tracedFireAllEvolve`, `causalDAGOfFireAll` and `branchialDAGOfFireAll`. When matches overlap it is not a Wolfram model update, and the edge count of a rule with |LHS| = |RHS| can change.
- The modules `MultiRuleDiscovered`, `StepZeroAncestor`, `H9Bridge`, `H9BridgeStepProof`, `H9Closure`, `H9StructuralProgress`, `DistinctEdgeIdentity`, `PartitionClosure` and the multi-rule part of `UniversalAdditivity` state their results with the fire-all operator. These results do not describe Wolfram model evolutions.
- The "branchial" relation of `BranchialEventTrace` is contention between events of one step for a consumed edge. It is not the branchial graph of the Wolfram model.
- `allMatches` enumerates distinct bindings, so a state with two equal edges gives one match for a one-edge left-hand side where the Wolfram model gives two.

## 6. Tetrads, connections and curvature tensors on a hypergraph

A tetrad at a point p of a Lorentzian 4-manifold is a basis {e_0, e_1, e_2, e_3} of T_pM with g(e_a, e_b) = η_ab. A null tetrad {l, n, m, m̄} has l and n real and null, m complex, l·n = −1, m·m̄ = 1 and all other products zero. The Newman-Penrose scalars Ψ0-Ψ4 are components of the Weyl tensor in a null tetrad, and Ψ4 describes outgoing radiation.

A tetrad, a connection, parallel transport, the Riemann tensor and Jacobi fields require a tangent space at each point and a metric on it. A hypergraph has a vertex set, a set of hyperedges and the graph distance. The set of hyperedges at a vertex is not a vector space. Graph distance, ball counts and Ollivier-Ricci curvature are defined on metric measure spaces and apply to hypergraphs.

In G3 the tetrad is built from the spatial metric that the CCZ4 code evolves on the hypergraph mesh (§5, lines 3960-4329). G3 §6 reports rΨ4 for the pure Wolfram model evolution (lines 6210-6216) and does not state how it is computed from the hypergraph. Details: `notes/null_tetrad_resolution.md`.

G1 §3.2 assumes that hyperedges that are not parallel "can be considered to be orthonormal" (line 2065) and uses this assumption to transfer the definition of sectional curvature (lines 2065-2068). G1 does not define a bilinear form on hyperedges (FINDINGS S2 #5).

Constructions that could take the place of a tetrad on a hypergraph, such as a labelling of hyperedges by four directions or a frame bundle of a continuum limit, have no published construction. A frame bundle of a limit requires a convergence theorem of the kind listed in `notes/limit_toolkit.md`, which is OPEN for Wolfram model evolutions.

## 7. Open items for a hypergraph derivation of the Einstein equations

1. A construction of the components g_ab of a discrete metric from the causal graph.
2. A definition of δ/δg^ab on discrete states that converges to the functional derivative of the continuum (Γ-convergence: Braides; Alicandro and Cicalese).
3. A proof or a computation of causal invariance for each rule used. The multiway engine in `efficient_rewriting_final/` enumerates multiway evolutions and can compare the causal graphs of different paths.
4. A convergence theorem: the causal graphs of a rule from a seed s_0, with edge length ε_n → 0, converge in Gromov-Hausdorff distance to a Lorentzian manifold (M, g). No such theorem exists for any Wolfram model rule.
5. A sequence ε_n → 0 in place of ε = δ = 1 (G1 line 2061), or a non-asymptotic Ollivier-Ricci statement.
6. For rules without causal invariance, a statement about the family of causal graphs of the multiway evolution graph.
