# Lean physics formalisation conventions

This file surveys existing Lean physics formalisation projects and records the conventions this library follows.

## Existing projects

### Mathlib

The library uses:

- `Mathlib.Topology.MetricSpace.*`: `MetricSpace`, `PseudoMetricSpace`, `HausdorffDist`, and the partial `GromovHausdorff` API.
- `Mathlib.Geometry.Manifold.*`: charted spaces, `IsManifold`, tangent bundles.
- `Mathlib.MeasureTheory.*`: measure spaces and integrals.
- `Mathlib.Data.Multiset.*`, `Mathlib.Data.Finset.*`: the combinatorial base for hypergraphs.

Mathlib does not contain the following, which the library needs:

- Ricci, Riemann and Weyl curvature tensors.
- Pseudo-Riemannian (Lorentzian) structures.
- Optimal transport and Wasserstein distance tied to Riemannian geometry.
- Lorentzian Gromov-Hausdorff distance.

### HepLean

[HepLean](https://heplean.github.io/HepLean/) is Joseph Tooby-Smith's formalisation of high-energy physics. It covers the Standard Model, gauge theory, fermions and Lorentz transformations.

HepLean conventions relevant here:

- Index conventions: HepLean uses abstract tensor contraction.
- Units: natural units (ħ = c = 1), with explicit scaling factors where other units appear.
- Lorentzian signature: (+, −, −, −).

### Other efforts

- Classical mechanics and variational principles: small formalisations, no unified library.
- Quantum-mechanical Hilbert-space formalisations: mostly foundational.
- Topos Institute physics formalisations: categorical direction, relevant to a categorical treatment of multiway evolution.

## Conventions of this library

1. Namespace. All material is in `InfraFormalization.*`. The sub-namespace `Infra` holds the discrete-continuum approximation results. Quantum and branchial content is in `BranchialHilbert`, `BranchialSchrodinger`, `BranchialCanonical`, `FisherMetric` and related files.

2. Axioms and `native_decide`. The target for each theorem is axioms within `propext`, `Classical.choice`, `Quot.sound` and no `sorry`. The library uses `native_decide` in about 100 files; theorems that depend on it are PROVED-WITH-NATIVE-DECIDE and depend on an axiom generated by `native_decide`. `AxiomCheck.lean` prints axioms for selected theorems. [`THEOREM_STATUS.md`](THEOREM_STATUS.md) lists the status of every theorem cited in the prose.

3. Lorentzian signature. The continuum Lorentzian files (`LorentzianManifold.lean`, `CurvatureLocalCoord.lean`, `Schwarzschild.lean`, `FLRW.lean`) use (−, +, +, +). HepLean uses (+, −, −, −). Sharing types with HepLean requires a sign change.

4. Units. Natural units (ħ = c = G = 1), with explicit conversions where a paper uses other units.

5. Tensors. Curvature is in local coordinates (`MetricData n`, `ConnectionData n`). Abstract vector-bundle connections are not formalised.

6. Continuum types. Mathlib types (`ℝ`, `ℂ`, `ℝ × ℝ`, `EuclideanSpace`, `AddCircle`) are preferred. `BranchialHilbert S` is `EuclideanSpace ℂ S` and has Mathlib's `InnerProductSpace` instance. `Hypergraph.dist`, `circleDist` and the lattice distances are plain functions with no `PseudoMetricSpace` instance.

7. Hypergraphs. `Hyperedge V` is a nonempty `List V` (a directed hyperedge). `Hypergraph V` is a `Multiset (Hyperedge V)`.

8. Single-way and multiway evolution. `Trajectory` is a chain of `Application`s of a rewriting system. `MultiwayCausalGraph` (`MultiwayCausalGraph.lean`) bundles a rewriting system with a causal DAG on events. `CausalHistory.lean` defines evolutions with hyperedge identities and their causal graph. The executable `MultiwayExec.singleWayStep` applies a maximal set of edge-disjoint matches, chosen greedily in enumeration order. `MultiwayExec.fireAllStep` applies every match, including matches that share edges, and is not a Wolfram model update when matches overlap. `MultiwayExecTests.lean` checks `MultiwayExec` against test cases transcribed from `../efficient_rewriting_final/tmp/TestCases.wl`.

9. Documentation. Each major definition and theorem has a doc-string stating what it says. Each file begins with a comment stating its purpose.

10. Proof style. Named intermediate hypotheses (`have h_foo : ...`) and explicit `calc` chains are preferred for user-visible theorems, with `simp` and `omega` closing goals. Single-tactic closures such as `aesop` are used for auxiliary lemmas.

## External theorems

A theorem proved elsewhere and not formalised here is stated as a Lean definition whose doc-string cites the source. Example: `OllivierIdentityLeading` (`Infra/OllivierStatement.lean`) states the leading term of Ollivier's identity (JFA 2009, Example 7). Comparisons such as `Infra.ollivier_gorard_agree_iff` are PROVED about these statements; the cited theorems themselves are not formalised.

## Upstream contributions

Constructions that generalise beyond this project, for example `GHApproximation` (`Infra/GHApprox.lean`), are candidates for Mathlib pull requests.
